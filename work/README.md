# ISP RGB calibration target toolkit

This toolkit creates and evaluates an A4 camera/ISP color target using four ArUco markers.

## Files

- `generate_target.py` - creates the target PNG, exact-A4 PDF, and JSON geometry/config.
- `eval.py` - detects the four markers, samples every color patch robustly, prints statistics, and writes a debug image.
- `manual_click.py` - fallback GUI for manually clicking the four marker centers and saving a JSON override.
- `calibration_common.py` - shared helpers.
- `isp_color_target.pdf` - ready-to-print A4 target.
- `isp_color_target.png` - 300 DPI source raster.
- `isp_color_target_config.json` - patch geometry, marker IDs, expected RGB values, sampling definition.

## Dependencies

```bash
uv sync
```

The `uv` environment installs NumPy, OpenCV-contrib, ReportLab, and tqdm.
`reportlab` is only required for `generate_target.py`; evaluation/manual
clicking use OpenCV + NumPy.

## 1. Print the target

Print `isp_color_target.pdf` at **100% / Actual Size**. Disable `Fit`, `Shrink oversized pages`, or similar printer-driver scaling.

The PDF page itself is exactly A4 (210 x 297 mm). The raster embedded in it is generated by OpenCV at 300 DPI.

Important: the printed RGB patches are *intent values*, not a traceable colorimetric reference. A printer, ink/toner, paper, printer profile, and ambient light all alter the physical colors. For repeatable ISP tuning, use the same print, illuminant, exposure, and geometry. For absolute color calibration, use a characterized commercial target.

## 2. Evaluate a camera image

```bash
python eval.py camera.png --config isp_color_target_config.json
```

This prints one row per patch with:

- expected RGB
- median measured RGB
- signed RGB error
- mean absolute error (MAE)
- RMSE
- similarity in percent
- within-patch RGB standard deviation

A debug image is written automatically beside the input as `camera_debug.jpg` (JPEG quality 90 by default). A PNG is only written if you explicitly pass `--debug some_file.png`. It contains:

- the input image with inferred patch/sample polygons and expected-color callouts
- a rectified A4 view where the small swatch in each patch is the expected color

The central 50% x 50% of each patch is sampled and the per-channel **median** is used. This avoids borders, label contamination, interpolation at patch edges, hot pixels, and moderate image noise.

Similarity is intentionally simple and interpretable in 8-bit RGB units:

```text
similarity = 100 * (1 - mean(abs(measured_rgb - expected_rgb)) / 255)
```

You can also save machine-readable results:

```bash
python eval.py camera.png \
  --config isp_color_target_config.json \
  --report-json camera_stats.json
```

To cache a successful ArUco detection for later reuse, save it in the same override format used by the manual tool:

```bash
python eval.py camera.png \
  --config isp_color_target_config.json \
  --save-markers-json camera_markers.json
```

The marker JSON contains each marker center, all four detected ArUco corners, each marker's rotation in degrees, and the combined chart rotation. It can be fed straight back into the evaluator:

```bash
python eval.py camera.png \
  --config isp_color_target_config.json \
  --manual-json camera_markers.json
```

## 3. Manual marker fallback

If the ISP is so distorted that ArUco detection fails:

```bash
python manual_click.py camera.png \
  --config isp_color_target_config.json \
  --output camera_markers.json
```

The manual tool is orientation-independent. Click the **marker centers as they appear in the image**, always in this order:

1. image top-left
2. image top-right
3. image bottom-right
4. image bottom-left

For a portrait A4 chart photographed in landscape, the tool automatically starts at a 90-degree chart rotation. After the fourth click, the inferred grid and expected-color swatches are overlaid. If the sheet was rotated the other landscape direction, cycle the mapping until the expected patches line up with the photograph.

Controls:

- `T` - rotate chart mapping clockwise by 90 degrees
- `G` - rotate chart mapping counter-clockwise by 90 degrees
- `S` or Enter - save
- `U` or Backspace - undo
- `R` - restart
- `Q` or Esc - quit

You can also force the initial orientation with `--rotation 0`, `90`, `180`, or `270`. The saved JSON records the selected chart rotation and is directly compatible with `eval.py --manual-json`.

Then evaluate with the saved override:

```bash
python eval.py camera.png \
  --config isp_color_target_config.json \
  --manual-json camera_markers.json
```

## Regenerate the target

```bash
python generate_target.py --dpi 300 --output-dir . --prefix isp_color_target
```

The marker dictionary is `DICT_4X4_50`, using IDs 10, 20, 30, and 40. Geometry is mapped with a 4-point homography, so small perspective/rotation errors are handled automatically even though the intended setup is perpendicular.

## 4. Run the resumable Radxa ISP sweep

`markers.json` is already a reusable marker override, so the sweep does not
run ArUco detection for every image. Run this on the Radxa from this directory:

```bash
uv sync
uv run python sweep_and_eval.py ./dataset
```

The default search has 40 candidates: CCM blends `0.00, 0.25, 0.50, 0.75,
1.00`, combined with automatic white balance and manual temperatures
`3200, 4000, 4800, 5600, 6400, 7200, 8000 K`. The expanded runner also
supports Cartesian sweeps of the two Bayer colour-gain ratios and an
output-space CCM saturation/hue transform:

- `--rg-gains` and `--bg-gains` patch the profile's four Bayer gains
  `(R, Gr, Gb, B)`, with the green gains held at unity. Values are ratios,
  so `0.8` means 80% of the red/blue gain relative to green.
- `--ccm-saturations` applies `L + s(I-L)` to each CCM bank, where `L` is the
  Rec.601 luminance projection. `1.0` is unchanged.
- `--ccm-hue-degrees` rotates the output colour axis around luminance using a
  Rodrigues rotation. `0` is unchanged; positive and negative values can be
  tested symmetrically.

For example, a focused first pass around the current best CCM is:

```bash
uv run python sweep_and_eval.py ./dataset \
  --blend-start 0 --blend-stop 0 --blend-step 1 \
  --rg-gains 0.60 0.80 1.00 1.20 1.40 \
  --bg-gains 0.60 0.80 1.00 1.20 1.40 \
  --ccm-saturations 1.0 --ccm-hue-degrees 0 \
  --awb-temperatures 4800 5600 6400
```

That is 75 captures. After selecting the best gain pair, hold those two
values and run a 5 x 5 CCM refinement, for example
`--ccm-saturations 0.80 0.90 1.00 1.10 1.20` and
`--ccm-hue-degrees -20 -10 0 10 20`. A literal full Cartesian product grows
very quickly, so the staged approach is usually more informative and keeps
the dataset to a practical size.

Each candidate is stored in `dataset/samples/NNNN-.../` with:

- `settings.json` - exact candidate, capture, chart, and profile metadata;
- `isp_profile.bin` - the profile actually installed for that sample;
- `capture.jpg` - the tenth captured frame;
- `eval.json` and `eval.txt` - patch statistics and the evaluator output;
- `debug.jpg` - compressed overlay/rectified evaluation image;
- `capture.log` and `eval-errors.txt` - diagnostic logs.

The root `checkpoint.json` is atomically updated after setup, capture, and
each of the ten frame conversions. Re-run the same command and dataset path
to resume; completed candidates are skipped. `summary.tsv` provides one row
per evaluated sample, including mean/median similarity, MAE, RMSE, signed RGB
bias, and the worst patch. The evaluator's similarity is
`100 * (1 - mean absolute RGB error / 255)`; lower MAE/RMSE and higher
similarity are better.

The runner intentionally keeps the driver's `SRGGB10` CFA unchanged. CFA
order is not a field in the vendor ISP profile (`libisp_ini` exposes Bayer
gains but no Bayer-pattern setter), so testing RGGB/GRBG/GBRG/BGGR requires
separate sensor-driver/device-tree experiments rather than profile samples.
The runner does not search gamma, contrast, sharpening, or denoise. The ten-frame
raw file is retained while a sample is incomplete and removed after its JPEG
and evaluation have been written, avoiding many gigabytes of long-term disk
use.
